# M3: per-file history, compare, rewind and tracking (complete)

M1 and M2 remain closed. M3 adds `loops`, `compare`, `rewind`, `pin`, `unpin`,
`track` and `untrack`. M3 is complete; M4 is next.

## Built

- File-scoped IDs, relative time and unambiguous message selection; HEAD and
  working versions; unified terminal-colored differences and provenance.
- Single-file atomic rewind with a durable safety loop, undo, deleted-file
  recreation and undo-to-absence; preserved existing modes and saved Unix modes.
- Batch local-time preview/confirmation, without holding a lock during the prompt;
  bounded memory, protected immutable targets and all backups before any write.
- Explicit worktree-specific tracking without staging or walking unrelated trees;
  Git ignores respected; untrack retains history and Git-tracked membership.
- Git-native rename detection. Explicit save detection compares the index to HEAD,
  disables external diff/text conversion/lazy fetch, and never stats the whole tree.
- Renamed-file HEAD and older committed baselines follow Git's own rename history;
  a missing new filename is not mistaken for proof that the file never existed.
- Transactional M2-to-M3 schema migration, temporary pin leases recovered under
  the repository lock, one-shot self-write markers and interrupted-rewind recovery.

Binary/large/secret/link working files and binary/large targets are refused for a single-file rewind and
reported as skipped in batch previews. A batch can be partial on I/O failure;
each completed file has an undo safety loop. If Git cannot detect a rename,
history stays at the old path. These behaviors are documented in the README.
Unknown untracked paths are refused for rewind, while known historical paths can
be recovered after untracking. GC preserves stat caches during an active rewind;
insufficient room fails safely rather than removing self-write suppression state.
