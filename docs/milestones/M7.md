# M7: native Git workflows (in progress)

The owner's current instruction is to finish the core amendments and every M7
acceptance gate, then stop. M8, M9 and S (cloud-system discovery and planning)
remain pending. Cloud research starts only after M7 is accepted; no cloud system
is being built in this milestone.

M7 extends the M6 workspace with branches and tags, merge/rebase/cherry-pick/revert,
stash, remote fetch/pull/push, per-file Git history and blame, and conflict
resolution. Interactive rebase remains a terminal operation, with guidance in
the UI. The per-file **loop** timeline and multi-file swimlanes remain M8.

The first implementation is under validation. It is not an accepted milestone
or a release candidate. The existing local browser demo still serves the M6
backend; it is not switched to an untested M7 binary.

All actions use typed requests and native Git. Clients cannot submit arbitrary
arguments, patches or executable commands. Progress streams are authenticated,
bounded and reconnectable. A session owns its running Git process trees and
cancels/reaps them on explicit cancellation or session shutdown. Mutations from
the UI are serialized, including staging and commit operations.

Destructive actions first return a stored, expiring confirmation plan. Execution
checks the action and repository fingerprint again; stale plans return HTTP 409.
The preview lists affected contents, references, safety eligibility and skipped
protection. Working and staged versions are saved separately where permitted,
using existing atomic blob writes, synchronization, locking and self-write
suppression. No loop-store lock is held while a remote operation runs.

A force push always uses an explicit `--force-with-lease=ref:observed-object-id`.
Its preview uses the locally observed remote-tracking tip; fetch first if that
tip does not exist. It never performs an unowned network request during preview.
Binary/secret/oversize content is never silently claimed to be protected by a
text safety loop. Conflict resolution preserves recoverable native Git stages
and refuses an unsafe overwrite when no supported recovery exists.

The final hook-safety follow-up reuses mandatory index-only stripping after
native pre-commit, prepare-commit-msg and commit-msg hooks when a UI action
continues a merge. Original hook failures still block the operation; working
bytes and hook files remain untouched. Rebase has a necessary restriction:
remove a message marker from a resolved working file and restage before
Continue. Paradox detects marked staged resolutions without mutating the index,
working bytes or HEAD, because native Git can select its rebase tree before
commit hooks. A rebase prepare hook changing that selected tree is refused;
that user's hook may already have changed the index. Clean rebase continuation
retains native hooks. Six real CLI regressions cover these cases.

Windows validation also exposed two handle-lifetime issues. SQLite now closes
its WAL/SHM connection before releasing the loop-store lock. Legacy migration
checks old store/watch locks and uses a stable common-dir migration gate; on
Windows it closes its old handles immediately before the atomic rename, still
holding the external gate. Tests cover repeated concurrent store opens, active
legacy-lock refusal and simultaneous initializers without losing IDs or bytes.
There is no copy/delete migration fallback. Older binaries must stay stopped
during migration because they cannot honor the new gate.
