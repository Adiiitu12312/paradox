# M2: loop storage and capture (in progress)

M1 remains accepted. M2 is not complete until its functional and performance
checks pass on all three operating systems. Its timing limits remain 50 ms for
a single-file save and 500 ms for a warm 50,000-tracked-file scan.

## Implemented

- `paradox loop [file...]`, `--stats` and `--gc`; save errors are nonfatal and
  written to a bounded log.
- BLAKE3-addressed zstd blobs behind `BlobStore`, atomic durable writes, SQLite
  WAL with FULL synchronization, schema guards and repository write locking.
- Tracked-only fallback scans, stat caching, latest-content dedup, secret/binary/
  size/link skips, worktree-isolated records with shared blob storage.
- Conservative allocated-blob accounting, oldest-unpinned eviction, protected
  pinned history, orphan/partial-file recovery and content-integrity checks.
- First-line messages including closed CSS/HTML forms and spaced SQL markers;
  stale-message labels, JSON auto-labels and shebang/PHP second-line handling.

Automatic hooks, staged-content stripping and commit retention arrive in M4.
The manually started watcher arrives in M4.5. No background process is started.

## Verification so far

[Run 38683662057](https://github.com/Adiiitu12312/paradox/actions/runs/38683662057),
source `1a862fc`, passes formatting, clippy and functional tests on all three OSes.
These include injected process aborts during blob/index/GC writes, retry and
integrity verification, 20 concurrent saves, worktrees, bounded storage and pins,
message property tests, Git parity and interactive-terminal checks. Dependency
audit passed. Every Paradox invocation uses a new temporary repository outside
the project.

| Linux | 5.240 ms | 196.300 ms |
| macOS ARM64 | 21.932 ms | 276.242 ms |
| Windows | **88.559 ms (fails)** | **1378.703 ms (fails)** |

The preceding Windows run (`d545062`, run 38682310057) passed functional checks
but measured 85.306 ms saves and 1435.553 ms warm scans, failing both limits.
Opt-in `PARADOX_PROFILE_CAPTURE=1` diagnostics now identify the cost of Git
discovery, store opening, tracked-set loading, dirty-state checks, file capture
and final durability work. Default execution remains silent. On Windows the
sampled save spent 35.626 ms in Git discovery, reached 38.282 ms after opening
the store and finished at 82.790 ms after capture. The median includes process
startup/exit. Scan diagnostics attributed roughly 1.24 seconds to serial file
metadata checks. A bounded eight-worker Windows stat pass and lazy baseline
dirty-set lookup are under validation at `b5f9a7f`; safety settings are unchanged.

## Local Windows demo

The 4,155,392-byte development binary from the diagnostic run was downloaded;
no compiler or Node installation was needed. With existing Node v26.4.0, a new
OS-temp repository produced the following and was removed afterward:

```text
PASS closed CSS marker: adjust spacing
PASS identical save: one loop
PASS stale marker: +1 -1
PASS tracked secret skipped; working bytes unchanged
loops=2 bytes=118784
```

The local check inspected the read-only SQLite index after each sequence and
confirmed capture did not modify working-file bytes. This is functional evidence,
not a passing Windows performance claim.

The brief update is applied: watcher requirements and tests are required in
M4.5, agent-rule printing in M4, new message forms in the shared parser now and
the future staged-content stripper. Finished M1 work is not restarted.
